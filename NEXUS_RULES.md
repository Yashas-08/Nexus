# NEXUS PROJECT CONSTITUTION

This is a persistent project-level instruction set, not a feature implementation task.

Authoritative source for all future NEXUS implementation work.

==================================================
PRODUCT
==================================================

NEXUS is a mobile-first consumer application that acts as a bridge between messy human intent and complex real-world systems.

Core flow:

Human intent
→ understand
→ structure
→ verify
→ prioritize
→ recommend action
→ user approval
→ action

NEXUS is NOT a generic chatbot.

AI should feel like invisible intelligence inside a useful product rather than the visual identity of the application.

==================================================
CODEBASE
==================================================

The existing repository is the single source of truth.

Always inspect the current implementation before changing it.

Build incrementally on the existing codebase.

Never restart the project or replace the architecture unless explicitly instructed.

Preserve working functionality.

Do not duplicate:
- components
- routes
- services
- authentication logic
- API clients
- utilities
- state management
- styles
- data models

Before creating something new, check whether an existing implementation can be reused or extended.

Modify the minimum number of files necessary for the requested task.

Do not make unrelated changes.

==================================================
ARCHITECTURE
==================================================

Frontend:
- React
- Vite
- TypeScript
- Tailwind CSS

Backend:
- Node.js
- Express
- TypeScript

Database and authentication:
- Supabase
- PostgreSQL through Supabase
- Supabase Authentication

AI:
- Gemini API
- Gemini API key remains server-side

Validation:
- Zod

Icons:
- Lucide React

Do not introduce additional frameworks, ORMs, state-management libraries, UI kits, or services unless they solve a demonstrated requirement that cannot reasonably be handled by the existing stack.

==================================================
SECURITY
==================================================

Never expose GEMINI_API_KEY to the frontend.

Never hardcode secrets.

Never commit .env files or credentials.

Use environment variables.

Frontend may use the Supabase publishable/anon key.

Never expose the Supabase service-role key to the client.

==================================================
DESIGN LANGUAGE
==================================================

NEXUS must feel like a polished real consumer mobile application.

Design priorities:

1. usability
2. visual hierarchy
3. spacing
4. alignment
5. typography
6. trust
7. simplicity
8. contextual actions

Use:
- restrained neutral colors
- strong typography
- generous whitespace
- carefully proportioned rounded surfaces
- subtle borders
- subtle shadows
- consistent spacing
- consistent corner radii
- native-feeling mobile interactions
- contextual content
- progressive disclosure

Do NOT make NEXUS look like:
- a CRM
- a SaaS dashboard
- an enterprise admin panel
- a generic AI dashboard
- a ChatGPT clone
- a futuristic AI interface
- a hackathon template

Never use:
- excessive gradients
- neon colors
- glowing borders
- glassmorphism
- floating AI orbs
- robot illustrations
- unnecessary futuristic graphics
- excessive cards
- excessive badges
- giant dashboards
- unnecessary animations
- repeated "AI-powered" labels

The interface must not look obviously generated by AI.

==================================================
MOBILE
==================================================

Mobile is the primary platform.

Design and test for:

320px
360px
390px
412px
430px

No:
- horizontal scrolling
- clipped content
- overlapping elements
- inconsistent alignment
- accidental overflow
- fixed elements covering content

Every interactive element must have appropriate touch targets.

Desktop may adapt naturally, but the product must remain a mobile consumer experience rather than becoming a desktop dashboard.

==================================================
UI QUALITY
==================================================

Every screen must have deliberate alignment.

Inputs sharing a form must have identical widths, heights, padding, radius, and typography.

Buttons must align precisely with their related content.

Spacing must follow a consistent system.

Typography must have a clear hierarchy.

Do not place elements simply because there is empty space.

Every element must have a product reason.

Avoid visual clutter.

Never use "e.g." or hypothetical example text in user-facing placeholders, inputs, or labels. Use direct, actionable instructions instead.

Temporary sample data is permitted only during initial UI prototyping; once the app is completely built, all mock/sample data must be completely removed and backed by real database/API records.

==================================================
PRODUCT PRINCIPLES
==================================================

Human intent comes first.

The user should not need to understand:
- AI models
- prompts
- agents
- tools
- APIs
- system architecture

NEXUS should understand the user's situation for them.

AI output must distinguish between:

VERIFIED
Information supported by available evidence.

USER REPORTED
Information provided by the user but not independently verified.

INFERRED
Information derived by the system and clearly presented as inference.

UNKNOWN
Information that cannot currently be established.

Never present an inference as a verified fact.

Never invent evidence.

Never claim an external action happened unless the application actually performed or successfully simulated that action.

==================================================
AI ARCHITECTURE
==================================================

Gemini is responsible for interpretation and reasoning.

Application code is responsible for:
- validation
- state management
- deterministic rules
- safety boundaries
- rendering
- action state
- error handling

Do not blindly trust arbitrary Gemini output.

Use structured responses.

Validate AI responses before using them in the application.

Keep deterministic business logic outside the model wherever practical.

==================================================
IMPLEMENTATION DISCIPLINE
==================================================

Every future implementation task must follow this sequence internally:

1. Inspect the existing code.
2. Identify the exact affected files.
3. Understand existing dependencies and architecture.
4. Implement only the requested change.
5. Reuse existing code where appropriate.
6. Avoid unrelated refactoring.
7. Run the application.
8. Test the affected functionality.
9. Check for regressions.
10. Fix issues before reporting completion.

Do not declare a feature complete simply because the code was written.

It must be verified.

==================================================
PROMPT DISCIPLINE
==================================================

Future implementation prompts will describe only NEW work.

Do not repeat this constitution in every task.

Do not repeat the entire architecture in every task.

Do not repeat completed phases.

Do not recreate completed features.

Each phase must build directly on the previous implementation.

If an existing feature must be modified, identify the exact reason and required change.

==================================================
ERROR PREVENTION
==================================================

Prefer simple, reliable implementations over unnecessary complexity.

Do not make speculative changes.

Do not install dependencies without a concrete requirement.

Do not change working configuration without a reason.

Do not create duplicate implementations to solve an existing problem.

If the current implementation conflicts with a new requirement, inspect it first and modify the smallest appropriate surface.

==================================================
REFERENCE IMAGES
==================================================

When design reference images are provided:

Use them as visual inspiration only.

Extract:
- spacing principles
- typography principles
- visual hierarchy
- interaction patterns
- competition quality

Do NOT copy:
- exact layouts
- branding
- wording
- icons
- proprietary visual identity
- screen structure
- element placement

NEXUS must remain its own product.
